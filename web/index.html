Introduction

AWS policies are hard to read. A single wildcard or a forgotten permission can let someone become an administrator. iam-trace works out what your policies actually allow and shows you why, with the statement that decided each answer.

What it answers

  • Attack paths: if someone takes over this user or role, can they reach full control of the account, and how?
  • Who can: who in the account can perform this action on this resource, directly or by escalating?
  • Policy check: what in this policy is risky, and how do I fix it?
  • Evaluate a request: is this one request allowed or denied, which policy decided it, and what would change the answer?
  • Policy diff: what does a policy change add or remove, in plain terms?

How it works

An engine that follows AWS's own evaluation order reads your policies: explicit denies, organization guardrails, resource policies, identity policies, permissions boundaries and session policies. The attack-path analysis checks every user and role against 91 published privilege-escalation techniques from pathfinding.cloud. Every answer is something you can check: the trace names the statement, and suggested fixes are verified by evaluating again.

Everything runs inside this browser tab. Your files are never uploaded, and you don't need to give iam-trace any AWS access.

Your first analysis

About five minutes, start to finish.

  1. Export your account. In a terminal with read access to AWS, run the command below. It saves a file called auth-details.json.
  2. Open Data input (left menu) and drop the file onto the page.
  3. Pick who the attacker is. Choose the user or role you are worried about, for example a developer whose keys could leak.
  4. Press Run analysis. The Overview tells you straight away whether that principal can reach admin.
  5. Explore. Open the Attack graph to see each step, and Findings for the full list.

Attack paths

AnswersCan this principal become an administrator, and how?Use it whenreviewing an account, after a key leak, or before granting a role new rights.You needan account export. SCPs are optional.

How it works

iam-trace knows 91 privilege-escalation techniques, collected by pathfinding.cloud. A technique is a trick such as "pass an admin role to a new EC2 instance, then read its credentials". For each user and role, iam-trace checks which techniques its policies allow, then chains them together: user A can become role B, role B can become role C, and so on, until it reaches someone with full control.

Reading the results

  • Overview gives the verdict first. Critical means a confirmed path to admin exists.
  • Attack graph draws the path. Click a principal or a technique label (like sts-001) to see the details and the AWS permissions involved.
  • Recommended fixes list the permissions to remove or narrow, ordered by how many paths each one breaks.
  • Findings lists every technique for every principal, so you can search and export them.

Confirmed or possible?

Confirmed means the policies in your export fully allow the technique. Possible means it also depends on something the export does not describe, such as an existing Lambda function and the role it runs as. Possible techniques are drawn as dashed amber lines. Check those resources yourself, or add a resource inventory so iam-trace can.

Steps that need MFA or a network

Policies often allow something only with MFA, from an office IP range or through a VPC endpoint. iam-trace tries the values those conditions name. A step that needs only values the attacker picks, such as the region or a tag on the request, is open. A step that needs MFA, a network location or a time window is gated: it is drawn as a dotted orange line with a label such as MFA, and its path says Needs MFA. Stolen access keys can't follow a path that needs MFA; a stolen session that signed in with MFA can. Open paths are listed first, and only an open path makes the verdict critical. Tags on users and roles in the export are used too, so conditions on principal or role tags are judged correctly.

Where an attack starts

The analysis starts from the principal you choose. Entry points on the Overview says which one an attacker would choose: IAM users, whose keys or password can leak, and roles that someone outside the account can assume. Each role's trust policy is tested with the evaluator, for example: can a GitHub workflow in a repository you don't own assume this role? One in another repository of your organisation? Any identity of this OIDC provider, a principal in an unrelated AWS account, or the named account without an ExternalId? Each one is rated by how open it is and what it reaches. Analyse from here runs the analysis from that principal.

The most common finding is a GitHub Actions role whose trust policy checks the token's audience (aud) but not its subject (sub). Every GitHub repository in the world can then assume it. The fix is a condition on token.actions.githubusercontent.com:sub naming your repository and branch.

Fix plan

The Fix plan card gives the fewest changes that remove every open path to admin, from the starting principal or from every principal. Each change is a Deny statement, scoped to the role, user or policy the step targets wherever possible, since denying a permission everywhere breaks more of what the principal legitimately does. iam-trace finds the cheapest set (a minimum hitting set over every route to admin), adds the statements to a copy of the account and runs the whole analysis again. Only a plan that leaves no path is marked Verified.

Each change says what the principal can no longer do and names the statement that grants the permission, if you would rather narrow that statement than add a Deny. Show on graph cuts the steps so you can see the result; Download policies saves them as JSON.

Apply as switches between three forms of the same fix, each verified separately: Deny statements; Narrow the Allow, which rewrites the statements that grant the permissions (removing an action, or limiting it to the resources that should keep it) and names anything else the edit stops allowing; and One SCP for AWS Organizations, limited to each principal with aws:PrincipalArn. Paths that need MFA or a network location are left alone unless you choose Cut them too: access like that is usually intended, such as break-glass admin with MFA.

Example

In the sample account, the user dev can assume the role ops (technique sts-001). ops can launch an EC2 instance with the ec2-admin role attached and read its credentials (ec2-001). ec2-admin has full access. So dev reaches admin in two steps:

result
user/dev --[sts-001]--> role/ops --[ec2-001]--> role/ec2-admin
         allowed every action on every resource

Removing either step breaks the path. Narrowing iam:PassRole on ops is usually the least disruptive fix.

What if I remove this step?

Select a technique label on the graph and choose Cut this step, or use Simulate next to a recommended fix on the Overview. iam-trace searches every confirmed step in the analysis again and tells you whether the attacker still reaches admin. If another route exists, it is drawn on the graph so you can cut that too. Cuts only change the view: the analysis and your saved data stay as they are. Run the analysis again after you change the policies to confirm the fix.

Sharing the result

Download report on the Overview or the graph saves one HTML file: the verdict, the shortest path from each starting principal, what to fix first, every principal at risk, and what the analysis did and did not cover. It contains no scripts, opens without a network connection and prints to PDF. It does include principal names and the account ID, so treat it like the export it came from.

Evaluate a request

AnswersIs this one request allowed? Which policy decided it?Use it whena request is denied and you don't know why, or before relying on a permission.You needthe principal, action, resource and the policy documents involved.

How to use it

  1. Fill in who (principal ARN), what (action, like s3:GetObject) and on what (resource ARN).
  2. Add the policies that apply. Open a row such as "Identity-based policy" and paste the JSON. Leave the rest empty.
  3. If a policy has conditions, add the matching context keys, such as aws:SecureTransport=true.
  4. Press Evaluate.

Reading the result

The banner says Allowed or Denied and why. Below it, the seven checks AWS makes are shown in order. The path lights up to the step that decided, and the trace table shows the exact statement that matched. Click any step to highlight it.

What would change this

Under the verdict, iam-trace says what would change the answer. It changes one thing at a time and evaluates again, so everything it suggests is checked:

  • Denied: the smallest fix. Remove or narrow the Deny, send a context value, or add the missing Allow to each layer that refused, written out as JSON. Try this change applies it to your request and evaluates again.
  • Allowed: what the decision depends on: the only statement that grants it, or the context keys that would deny it if they changed.
  • Near misses: Allow statements that name the action but fail on the resource or a condition. Usually the typo.

How AWS decides, in short

  1. Any explicit Deny wins. If any policy denies the request, it is denied.
  2. Organization guardrails (RCPs and SCPs) must allow it.
  3. A resource policy, such as a bucket policy, can grant access on its own.
  4. Identity policies on the user or role must allow it otherwise.
  5. Permissions boundaries and session policies can only narrow what identity policies allow.

If nothing allows the request, it is denied by default. Requests across accounts need an Allow from both sides.

Who can

AnswersWho in this account can do this action on this resource?Use it whenreviewing access to something sensitive: a bucket, a key, an admin role.You needan account export loaded in Data input.

Enter an action and a resource. Every user and role in the export is evaluated with the same engine as Evaluate, and grouped:

  • Directly: their own policies allow it. The statements that grant it are listed.
  • Through escalation: they can't do it themselves, but have a confirmed path to someone who can. These are the ones to look at first.
  • Outside the export: principals the resource policy names that the export doesn't contain, such as another account or anyone (*).

The access graph above the lists shows every route to the resource: principals that must escalate on the left, with each hop labelled by its technique, then the principals with direct access, then the resource. Principals outside the export join on a dashed line. Select one to find it in the lists.

Paste the resource's own policy (a bucket or key policy) under the optional section to include it. SCPs and the resource inventory from Data input are used automatically.

Policy check

AnswersWhat in this policy is risky, and how do I fix it?Use it whenwriting or reviewing a policy, or auditing every policy in an account.You needone or more policies, or an account export.

Policy check reads each policy on its own and flags patterns that commonly lead to trouble. Every finding says where it is (policy and statement), why it matters and how to fix it.

It catches things like full administrator access, iam:PassRole on any role, Allow with NotAction, trust and bucket policies open to "Principal": "*", conditions that pass when a key is missing, trust policies that let any GitHub repository (or any identity of another provider) assume a role, and actions that match nothing. A typo in a Deny is the worst case: the policy looks safe but protects nothing.

Severity is High, Medium or Low. If a statement has a condition the rule doesn't look for, the finding drops one level and says so, because the condition may narrow it.

Check an account export and every customer managed policy, inline policy and trust policy is checked once, with the users, groups and roles it's attached to. AWS managed policies are skipped unless you turn them on: they are broad by design.

Policy check looks at one policy at a time. It can't see what else a principal has, so a clean result doesn't prove least privilege. To see what an attacker could actually reach, use Attack paths.

Policy diff

AnswersWhat does this policy change actually grant or remove?Use it whenreviewing a pull request that edits a policy.You needthe policy before and after the change.

A text diff shows which lines moved. iam-trace compares what each version allows, so reordering statements, renaming Sids or splitting a statement in two shows as no change, while widening a resource or dropping a condition shows as newly allowed.

Every change lands in one of four groups: newly allowed, no longer allowed, newly denied and deny removed. Within each group, actions are sorted by access level.

Actions marked Sensitive deserve a second look: they manage permissions or appear in known escalation techniques. iam:PassRole is the classic example. AWS calls it a plain "Write" action, but it is how most escalations start.

Getting your data

Attack paths needs one file, produced by a single read-only AWS command:

terminal
aws iam get-account-authorization-details --output json > auth-details.json
  • Permission needed: iam:GetAccountAuthorizationDetails. The AWS managed policy SecurityAudit includes it.
  • What's inside: every user, group, role and managed policy in the account, with the policy text. No passwords or keys.
  • Treat it as internal: it describes how your account is set up.
The export does not include your organization's SCPs. If the account is in AWS Organizations, add them under Organization SCPs in Data input. SCPs can block a path, so results without them may overstate the risk.

Buckets and keys

The same inventory also records your S3 buckets (with their bucket policy, default encryption key and Block Public Access settings) and customer managed KMS keys (with their key policy). Data access then rates each one by who can read and write its data, directly, by escalating or from outside the account. Reading an encrypted bucket takes kms:Decrypt on its key too, so a role that can fetch objects but can't decrypt them is listed separately.

Optional: a credential report

The account export doesn't say which users have access keys or a password, so Entry points lists every user. The IAM credential report says, with dates. Get it read-only:

terminal
iam-trace credentials collect --out credentials.json

Load it under Credential report in Data input. Users with no password and no active key are left out of Entry points, old or unused keys and passwords without MFA rank higher, and root user access keys are reported as critical. The report holds dates and flags, no secrets.

Optional: last accessed data

IAM records when each user and role last used each service it is allowed, over the last 400 days. Get it read-only:

terminal
iam-trace usage collect --auth-details auth-details.json --out last-accessed.json

Load it under Last accessed in Data input, then open Unused access. A service is removed from a policy only if nobody who has the policy, directly or through a group, used it for the number of days you choose (90 by default). Edits only take access away: a statement that allows everything becomes "everything except the unused services", so services the data doesn't cover stay. iam:PassRole is never removed, because AWS doesn't record when a role is passed. The account is then analysed again, to show which paths to admin the cleanup closes. Roles kept for emergencies look unused by design; review each edit before applying it.

Optional: a resource inventory

Some techniques take over something that already exists, such as editing an existing Lambda function's code to act as its role. The export doesn't list your functions or instances, so these are possible until you add a resource inventory:

terminal
iam-trace inventory collect --out inventory.json

It runs read-only list and describe calls through your AWS CLI and records each Lambda function, EC2 instance and launch template, CodeBuild project, CloudFormation stack, Glue dev endpoint, SageMaker notebook, Step Functions state machine, App Runner service, Batch job definition, running ECS task and Bedrock AgentCore resource with the role it runs as. Load the file under Resource inventory in Data input. Findings then name the exact resource, and techniques with nothing to take over disappear. If a kind couldn't be collected, it stays possible instead of being treated as empty.

GitHub Action

Add this workflow and every pull request that changes a policy file gets a review comment: what the change grants, any new escalation technique, and any risky pattern the change introduces. It can also fail the check.

.github/workflows/iam.yml
on: pull_request
permissions:
  contents: read
  pull-requests: write
jobs:
  iam:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: w3bcooki3/iam-trace/action@main
        with:
          paths: "policies/**/*.json"
          fail-on-escalation: "true"
          fail-on-diff: "never"   # or any | new-allow | highlighted
          fail-on-check: "high"   # or never | medium | low
SettingMeaning
pathsWhich files are policies, as comma-separated glob patterns.
fail-on-escalationFail if a changed policy allows a technique the old version did not.
fail-on-diffAlso fail on diff results: never, any, new-allow or highlighted (sensitive).
fail-on-checkFail if the change introduces a Policy check finding at this severity or higher: never, high, medium or low. Problems already in the old version don't count.
terraform-planA Terraform plan in JSON (terraform show -json plan.out, from an earlier step). Its IAM changes are reviewed in the same comment.
auth-detailsThe current account export. With a plan, the plan is applied to it and new paths to admin and new entry points are reported.
fail-on-terraformFail when the plan does this: never, new-path (the default), new-entry-point, escalation, check-high or any.
commentPost or update one review comment on the pull request.

The Terraform plan screen gives the same review in the browser; Copy as PR comment copies it as Markdown.

Output and exit codes

Every command prints readable text by default. Add --format json for scripts or --format sarif for GitHub code scanning; diff also has markdown. In the app, use Download report on the Attack graph or the buttons on Findings and Policy check.

Exit codeMeaning
0Success. For can: the request is allowed.
1For can: denied. For check, diff and escalate: a --fail-on rule matched.
2Something is wrong with the input: a usage error, an unreadable file, or a policy AWS would reject.

Privacy and security

  • Nothing is uploaded. The analysis engine runs inside this page. The page is only allowed to load files from its own site, and has no analytics.
  • Your work is saved in this browser. Exports, policies and your last analysis are kept in the browser's own storage (IndexedDB) so a refresh does not lose them. They never leave your machine. Turn saving off, or delete any of it, in Settings under Saved data. If the browser won't save (private browsing, for example), the top bar says "Not saved" and you are asked before leaving.
  • No AWS access needed. iam-trace only reads the files you give it.
  • Built for hostile input. Malformed or malicious policies produce clear errors instead of crashes or hangs.
  • Settings stay local. Your display choices are stored in this browser only.

Limitations

iam-trace is careful, but it is not AWS. Keep these in mind:

  • Not yet compared live with AWS. It passes AWS's documented examples and hundreds of tests, but the large comparison against AWS's own policy simulator has not been run yet.
  • Context keys you don't supply count as missing. Only principal and account keys are filled in automatically.
  • Some service rules are not modelled, such as S3 ACLs, Block Public Access, VPC endpoint policies and KMS grants.
  • One account at a time. Paths into other accounts are not followed.
  • Existing resources need an inventory. Without one, techniques that take over a function or instance are possible, not confirmed. With one, permissions are checked on the main resource only (not, say, a Batch job queue), and ECS tasks are those running when it was collected.

The repository's docs/limitations.md has the complete list.

Questions

Why "beta"?

iam-trace passes AWS's documented examples and hundreds of tests, but it has not yet been compared case by case with AWS's own policy simulator, and it has the limitations listed above. Use it alongside your existing reviews, not instead of them.

How does it relate to other tools?

iam-trace builds on pathfinding.cloud, Datadog Security Labs' library of escalation techniques, and links every finding to it. Other good open-source tools cover related ground: PMapper (NCC Group) maps escalation paths from the command line, Cloudsplaining (Salesforce) reports least-privilege violations, and iam-lens (Cloud Copilot) simulates requests across many accounts. iam-trace's focus is different: it runs entirely in the browser with no install or upload, explains every finding in plain language, and puts evaluation, policy diffs and escalation paths in one place, with a GitHub Action for pull requests. Use whichever fits your job; they work well together.

A technique shows as possible. What should I do?

Look at the resource it depends on, for example which role an existing Lambda function uses. If that role is powerful, treat the technique as real.

Can I use it in CI?

Yes. Use the GitHub Action, or the command line with --fail-on in any CI system.

Your files never leave this browser tab. You can check this yourself in your browser's network panel.
